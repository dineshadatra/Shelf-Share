# ShelfShare authentication and manual verification

## Implemented application design

- Passwordless Indian mobile sign-in uses Supabase Auth SMS OTP only. Email OTP and password sign-in are not called by the web client.
- OTP validity is configured to 300 seconds locally; the resend frequency is configured to 60 seconds. Supabase Auth owns the OTP generation, verification, expiry, resend throttling, and IP/project rate limits. The React countdown is only a user-interface hint.
- Access tokens use a one-hour JWT lifetime in the local configuration. Refresh-token rotation is enabled. Local session defaults are a 30-day maximum lifetime and 24-hour inactivity timeout. The client persists and refreshes the session; logout calls Supabase Auth signOut for the current browser session. Hosted session timebox/inactivity controls are plan-dependent and must be confirmed in the Dashboard.
- Phone changes use Supabase Auth updateUser({ phone }) followed by verifyOtp(type: 'phone_change').
- Registration requires a verified phone, display name, DOB >= 18, a camera-captured JPEG profile photo, and acceptance of the active Terms and Privacy versions.
- The registration RPC checks the verified phone timestamp and DOB in Postgres. Registration policies must be activated by an authorised product/legal operator before registration can complete.
- Identity documents are stored in private Storage buckets. Browser clients can upload only to their own user-prefixed paths. No client read policy exists for identity documents, selfie or private profile captures.
- Manual review is performed with the verification-admin Edge Function and the review_verification_case database function. Reviewer role, assignment and the cannot-review-own-account constraint are checked server-side. Suspension marks the profile suspended, clears the verified status used by listing/booking gates, and applies a long-duration Auth ban via the server-only Admin API. Reinstate/unban must remain a separate authorised operational decision.
- Marketplace listing and booking gates continue to depend on verified status in database policies/functions; UI state is not treated as authority.

## Provider and deployment steps

1. Apply migrations with `supabase db push` after reviewing the SQL against the target project.
2. In Supabase Authentication > Sign In / Providers, enable Phone and disable Email as a sign-in method. The local config sets `auth.email.enable_signup = false` as an additional guard; confirm the hosted provider toggle is disabled too. Configure an approved SMS provider and the India sender/template/DLT requirements applicable to your deployment.
3. Configure Cloudflare Turnstile in Supabase Auth > CAPTCHA. Put the public Turnstile site key in `VITE_TURNSTILE_SITE_KEY`, set `VITE_CAPTCHA_REQUIRED=true`, and keep the Turnstile secret only in Supabase Auth Dashboard CAPTCHA settings. The frontend passes the challenge token as `captchaToken` to phone OTP requests and blocks the request when CAPTCHA is required but missing. Local development may use `VITE_CAPTCHA_REQUIRED=false`; do not deploy with CAPTCHA disabled. Then configure the hosted limits to the checked-in baseline: 300-second OTP expiry, 60-second resend interval, 15 SMS per hour per project, 20 sign-in/sign-up requests per IP per five minutes, and 10 verification requests per IP per five minutes. These are initial protective settings; tune against real traffic and legitimate shared-network usage. Configure CAPTCHA/Turnstile before production launch.
4. Configure the hosted project's JWT expiry, refresh token rotation, reuse interval, 30-day maximum session lifetime and 24-hour inactivity timeout in the Dashboard. Supabase documents timebox and inactivity expiry as paid-plan controls; verify availability on the selected project plan. The checked-in TOML is for local Supabase development and is not automatically pushed to hosted Auth settings.
5. Add the Supabase project URL and publishable/anon key to frontend environment variables. Never put the service-role key in `VITE_*` variables or browser code.
6. Set the Edge Function secret `APP_ORIGIN` to the exact deployed frontend origin (for example, your production ShelfShare HTTPS origin). Deploy with `supabase functions deploy verification-admin`. Supabase supplies `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` to hosted functions; the service-role key is server-only.
7. Assign `verification_reviewer`, `admin`, or `super_admin` roles to actual reviewer users through a controlled back-office migration/process. No self-service role assignment is exposed.
8. After Terms and Privacy Notice have been reviewed and published, insert one active, approved row in `public.registration_policy_versions` with HTTPS URLs and distinct version identifiers. This intentionally blocks registration while legal copy is not approved.
9. Run `supabase test db` against a disposable local Supabase stack and `npm run build`, `npm run lint`, and `npm run test:security`.

## Important security boundaries and launch blockers

- A web browser's getUserMedia flow can require a live camera capture in the normal application path. A browser alone cannot cryptographically prove that a sensor feed is genuine or prevent a modified client from submitting a replayed image. The current capture is not biometric liveness/face matching. Add a specialist liveness provider if spoof resistance or regulated identity proofing is required.
- The uploaded live profile photo is kept private in this implementation. A public avatar derivative/consent policy has not been defined and is not generated.
- The optional address-evidence upload is a workflow attachment only. PAN is not treated as address proof. Accepted address evidence, when required, must be specified by the product/legal policy before reviewers rely on it.
- Supabase Auth applies platform OTP expiry, resend throttling, Turnstile CAPTCHA and request rate limits. The UI cooldown is not a security control. The configured verification request limit is IP-based, not a strict per-phone wrong-code counter; if ShelfShare needs a lower per-number failure threshold, add an SMS/OTP orchestration service or Auth hook before production. CAPTCHA must be enabled in hosted Auth and connected to the client before production.
- Admin access to documents is intentionally limited to short-lived signed URLs from a role-checked Edge Function, and each preview request is written to an access-audit table. Do not expose service-role credentials to the frontend.
- The initial reviewer implementation has role and self-review checks. Before launch, define maker-checker requirements, reviewer training, data retention/deletion periods, appeals, address verification standards, support SLAs, a controlled reinstatement/unban workflow, and a second-factor policy for staff.
- The SQL migration has not been applied to a live project by this change. Test it against the exact Supabase/Postgres version and existing migrations before enabling the app.
